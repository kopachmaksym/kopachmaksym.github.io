# Рецензія на API Animal-ID (партнерська відкрита платформа)

Оцінка на основі реальної інтеграції з живим API (Test-організація, `https://gw.animal-id.net/v1/partner`), 2026-07.

---

## 1. Що це за API

Відкрита платформа для ідентичності тварин: партнери (клініки, притулки) реєструють **власників** і **тварин**, шукають їх за **мікрочіпом/QR**, ведуть **медичні процедури**, керують **доступом за згодою власника** та отримують **вебхуки**. Ідея — єдиний глобальний паспорт тварини, спільний між клініками.

**Покриття функцій:** owners (create/resolve, search) · animals (create, get, lookup-by-identifier, by-owner, update) · procedures (вакцинації, стерилізація, дегельмінтизація, чіпування, евтаназія; list) · photos (upload/delete) · access-request (+webhook) · dictionaries. Для ветеринарного домену набір **повний і логічний**.

## 2. Дизайн API

- **Автентифікація — HMAC-SHA256 підпис запиту.** Канонічний рядок `METHOD\n{path}\nsha256(body)\n{timestamp}`, ключ — приватний ключ. Схема сучасна й безпечна (тіло входить у підпис, є захист від replay через timestamp ±300с).
- **Ідемпотентність** через `X-Eternity-Idempotency-Key` на всіх записах — правильно й по-дорослому: повтор безпечний, дублів немає.
- **Consent-first доступ.** До чужих тварин — лише через запит згоди власника + вебхук на рішення. Приватність закладена в дизайн, а не прикручена збоку — це сильно.
- **Вебхуки** підписані тією ж схемою — консистентно.
- **Словники** (`/dictionaries`) багатомовні (5 мов) — зручно для локалізації.

**Дрібні непослідовності дизайну:**
- `payload` у відповіді **завжди масив**, навіть коли ресурс один (створення owner/animal) — доводиться щоразу брати `[0]`.
- `expand` передається **заголовком** (`X-Eternity-Expand`, JSON-масив), а не query-параметром — нетипово.
- Пошук — параметр `email_or_phone`, хоча інтуїтивно очікуєш `email`/`phone`.

## 3. Документація

**Плюси:** описані ендпойнти, схема підпису, обов'язкові поля create-запитів, типи процедур.

**Мінуси (відчутні):**
- **Схема підпису недосказана:** не вказано, що ключ HMAC — це сам рядок ключа (а не hex-декодовані байти), і що `payload` завжди масив. З'ясовували пробами.
- **Лінкування власника до тварини** — у доках описано і `public_id`, і `user_gid`, але **на цій версії API працює лише `user_gid`** (public_id → 422). Розбіжність доків і реальності.
- **URL публічного профілю тварини не задокументований взагалі.** Правильний патерн (`/en/pets/<id>`) знайшли лише з реальної сторінки.
- Немає прикладів «повного» відповіді-конверта (`payload`/`metadata`/`links`/`message`).

Підсумок: доки **достатні, щоб почати**, але кількох ключових деталей бракує — без живих проб інтеграцію «наосліп» не зробиш.

---

## 4. Developer experience

- **SDK:** офіційні для PHP, JS/Node, React, Vue, Angular. **Python-SDK немає** — для Python-бекендів клієнт пишеться руками (втім, схема проста).
- **Помилки — сильна сторона.** `422` повертає структуровані `validation_errors` із **назвами полів і людськими повідомленнями**. Це дозволяє «намацати» контракт емпірично (порожній payload → перелік обов'язкових полів). Дуже допомагає.
- **Тестова організація = пісочниця.** Безпечно, з готовими демо-даними (є тварина для lookup одразу). Ідемпотентність робить повторні тести чистими.
- **Стабільність під час тесту:** API-шлюз (`gw.animal-id.net`) працював стабільно; але **публічний сайт `animal-id.net` періодично віддавав 502**, і **ріже не-браузерний User-Agent** — автоматичні перевірки з сервера падали, хоча в браузері все відкривалось.

---

## 5. Сильні сторони (підсумок)

1. **Повний, доменно-логічний набір функцій** для ветклініки.
2. **Безпека за замовчуванням** — підпис, ідемпотентність, consent-модель.
3. **Чудові помилки валідації** — контракт «читається» через відповіді.
4. **Пісочниця з демо-даними** — швидкий старт і безпечні тести.
5. **Багатомовні словники** — готовність до локалізації.

## 6. Слабкі сторони (підсумок)

1. **Прогалини в документації** — підпис, лінкування, URL профілю; розбіжність доків і реальної версії API.
2. **Немає Python-SDK.**
3. **Дрібні непослідовності контракту** — payload-масив, expand-заголовок, `email_or_phone`.
4. **Публічний сайт нестабільний** (502) і **блокує не-браузерні агенти** — заважає автоматизованій перевірці/моніторингу.
5. **Фото — складніший multipart-підпис** (окрема схема), поріг входу вищий за решту.

---

## 7. Наскільки API придатний до інтеграції (в т.ч. для ШІ)

API **добре піддається інтеграції**, і — що важливо — **дружній до ШІ-агента** саме завдяки якісним помилкам: агент може надсилати проби й **вичитувати контракт із `422`-відповідей**, а не вгадувати. Це компенсує прогалини в доках.

Обмеження для «повністю автоматичної» інтеграції — **не в API, а навколо нього:**
- потрібні креденшіали (див. п.8) — їх не згенеруєш програмно;
- недокументовані деталі вимагають **живого середовища для проб** (сам по собі текст доків недостатній);
- нестабільність/UA-блок публічного сайту ускладнює автоматичний моніторинг.

Оцінка: за наявності ключів і тестового доступу сучасний ШІ здатен інтегрувати цей API майже автономно; людина потрібна для видачі ключів і кількох продуктових рішень.

---

## 8. Активація доступу

Щоб узагалі почати, треба **створити сторінку організації** в Animal-ID (партнерський кабінет) — саме вона видає **App ID + публічний/приватний ключ + webhook-secret**. Без організації креденшіалів немає, і жоден виклик API неможливий. Це перший обов'язковий крок для будь-кого, хто хоче підключитись.

## 9. Підсумкова оцінка

**Міцний, продуманий API з правильними безпековими рішеннями і відмінними повідомленнями про помилки; головний недолік — прогалини в документації (підпис, лінкування, URL профілю) та нестабільність публічного сайту.** З живими пробами інтегрується без проблем; «наосліп» лише за доками — ні. Для ветеринарного домену — рекомендований до використання.
